# Wear OS — Этап 2: модель данных и миграции

## Выполнено

Этап 2 добавляет только серверный слой хранения для будущей интеграции часов. API,
экран подключения, выдача кодов и фактический pairing в этом этапе не реализованы.

Добавлены сущности:

- `WatchDevice` — привязанная к пользователю установка приложения на часах;
- `WatchPairingCode` — краткоживущая запись будущего pairing-процесса;
- `WatchSyncOperation` — журнал idempotency для повторной доставки операций с часов.

Для `ExerciseTemplateSet` добавлено поле `Version`. Это обычный целочисленный
optimistic concurrency token, совместимый с SQLite. При успешном изменении подхода
версия увеличивается приложением; EF Core включает предыдущую версию в условие
`UPDATE` и обнаруживает конкурирующую запись.

## Решения и ограничения

### Идентичность устройства

`WatchDevice.DeviceId` — стабильный идентификатор установки, создаваемый клиентом.
На него установлен глобальный уникальный индекс. Поэтому повторный pairing того же
устройства в будущем должен переиспользовать или передать существующую запись, а не
создавать дубликат.

В базе сохраняются только хеши pairing-кода и refresh token. Поля для хранения их
открытого значения отсутствуют.

### Владение и удаление аккаунта

`WatchDevice` и `WatchPairingCode` имеют обязательный внешний ключ на Identity user
с каскадным удалением. `WatchSyncOperation` каскадно удаляется вместе с
`WatchDevice`. Удаление пользователя поэтому удаляет весь Wear OS-граф средствами
БД.

### Idempotency и retention

`WatchSyncOperation.OperationId` является первичным ключом: повторная операция с тем
же ID не может быть записана второй раз. Запись содержит результат первой обработки,
чтобы будущий API мог вернуть его при повторной доставке.

Срок хранения операции — 30 дней (`WatchSyncOperation.RetentionPeriod`). Поле
`ExpiresAtUtc` и индекс по нему подготовлены для фоновой очистки. Сам фоновый процесс
очистки не входит в Этап 2 и должен быть добавлен вместе с рабочим sync-контуром.

### Pairing-коды

Хеш кода намеренно не глобально уникален: короткие коды могут безопасно повторяться
после истечения срока. Будущий pairing-сервис обязан исключать одновременно активные
коллизии и ограничивать попытки. База проверяет положительный интервал жизни и
неотрицательный `AttemptCount`.

## Миграция

Миграция `AddWearOsDevicePersistence`:

- добавляет `ExerciseTemplateSets.Version INTEGER NOT NULL DEFAULT 0`;
- создаёт таблицы `WatchDevices`, `WatchPairingCodes`, `WatchSyncOperations`;
- создаёт внешние ключи, уникальные и поисковые индексы, check constraints;
- сохраняет существующие подходы, присваивая им начальную версию `0`;
- в `Down` удаляет новые таблицы и столбец версии.

## Проверки

Интеграционные тесты проверяют:

- обновление SQLite с предыдущей миграции и сохранность существующего подхода;
- создание полного Wear OS-графа после миграции;
- глобальную уникальность `DeviceId`;
- уникальность `OperationId`;
- ограничения сроков жизни;
- каскадное удаление Wear OS-данных вместе с пользователем;
- реальный optimistic concurrency conflict между двумя `DbContext`;
- возврат актуального состояния подхода при устаревшей ожидаемой версии.
