# Этап 11. Полная страница подключённых устройств — результат

Дата завершения: 10 сентября 2026 года.

## Результат

Минимальный раздел `Профиль → Часы` расширен до полноценного управления Wear OS
устройствами. Этап 12 и SignalR-синхронизация не начинались.

## Реализовано

- создание нового шестизначного pairing code и отображение срока его действия;
- загрузка списка устройств только текущего авторизованного пользователя;
- отдельное отображение активных и ранее отозванных устройств;
- display name, модель, дата подключения и последняя активность;
- переименование активного устройства с валидацией имени от 1 до 120 символов;
- отзыв одного устройства и отзыв всех активных часов пользователя;
- обязательный диалог подтверждения перед отзывом;
- loading, empty, error и success состояния;
- responsive-компоновка на существующих переменных и визуальных компонентах
  приложения без отдельной дизайн-системы;
- refresh token, его hash и другие credentials в UI и management responses не
  выводятся.

## Management API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/watch/devices` | Получить устройства текущего пользователя. |
| `PUT` | `/api/watch/devices/{deviceId}` | Переименовать принадлежащее пользователю активное устройство. |
| `DELETE` | `/api/watch/devices/{deviceId}` | Отозвать конкретное принадлежащее пользователю устройство. |
| `DELETE` | `/api/watch/devices` | Отозвать все активные часы текущего пользователя. |

Все endpoints требуют main-app identity и не принимают `UserId` из запроса как
источник владения. Чужое, отсутствующее или уже отозванное устройство нельзя
переименовать. Массовый отзыв не затрагивает устройства других пользователей.

## Инвалидация credentials

При отзыве фиксируется `RevokedAtUtc`, refresh-token hash заменяется случайным
значением, а срок refresh token немедленно истекает. Поэтому прежний refresh token
возвращает `401`; уже выданный access token также отклоняется, поскольку watch
authorization policy проверяет актуальное состояние устройства в базе на каждом
защищённом запросе.

## Валидация

- Web/Test build с изолированным output: успешно, 0 ошибок; осталось одно
  существующее предупреждение Firebase об устаревшем `Message.Token`.
- Targeted management integration tests: успешно, включая валидацию имени,
  ownership boundary, rename, revoke-all, отказ прежним refresh/access credentials
  владельца и сохранение доступа у часов другого пользователя.
- Watch-фильтр integration tests: 10/10 успешно.
- Полный server suite: 70/72 успешно при параллельном запуске. Два несвязанных
  Telegram/admin теста столкнулись с существующей process-global гонкой
  `FirebaseApp already exists`; каждый из них затем отдельно прошёл 1/1.
- EF Core `has-pending-model-changes`: изменений модели относительно последней
  миграции нет; новая миграция не требуется.
- Браузерная проверка на временной SQLite-базе: список двух реально подключённых
  через API устройств загружен, metadata отображается, переименование сохранено и
  success state показан, диалог отзыва открыт и отменён без изменения данных.
- Узкая responsive-компоновка и диалог визуально проверены: критичной обрезки и
  горизонтального переполнения нет, основные действия остаются читаемыми и
  доступными для касания.

## Границы

- Wear OS-клиент, модели данных и миграции на этом этапе не изменялись в рамках
  management UI.
- Pairing-протокол не менялся.
- Физическая проверка на Wear OS-часах для веб-страницы управления неприменима;
  клиентские watch-сценарии остаются результатом Этапа 10.
- SignalR и Этап 12 не начинались.

## Стоп-условие

Пользователь может управлять подключёнными часами из основного приложения. После
завершения проверок работа останавливается на границе Этапа 11.
