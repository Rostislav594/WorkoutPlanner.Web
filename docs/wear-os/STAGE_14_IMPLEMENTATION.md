# Этап 14. Расширенный Wear OS UI и синхронизация

## Реализованный объём

К основному сценарию `Current set → Complete → Rest → Next` добавлены три вторичных
экрана: обзор активной тренировки, редактор индивидуального веса/повторов текущего
подхода и подробный список операций синхронизации. Доступен undo последнего
выполненного подхода. Завершение всей тренировки с часов не реализовывалось.

Экран текущего подхода сохраняет completion первым и самым заметным действием.
Редактор использует крупные явные степперы: 2,5 кг для веса и 1 для повторов.
Состояния pending, syncing, error и conflict названы текстом; retry предлагается
только для временной ошибки, а terminal/conflict запись можно убрать из списка.

## Offline-first и конфликты

Локальная очередь поддерживает `CompleteSet`, `UndoSet`, `UpdateWeight` и
`UpdateReps`. Изменение Room-состояния и постановка операции выполняются атомарно,
после чего один unique WorkManager job отправляет операции по глобальному
`sequenceNumber`.

Версия новой операции вычисляется как подтверждённая серверная версия плюс число
предыдущих нерешённых операций этого подхода. Соседние ещё не отправленные правки
веса/повторов объединяются. Не отправленные complete и последующий undo взаимно
отменяются. После начала отправки undo становится отдельной операцией.

Сервер остаётся источником истины. Успех заменяет локальный снимок авторитетным
ответом и сразу удаляет операцию. Временная ошибка допускает retry. Permanent failure
и `409 Conflict` остаются видимыми; конфликт также блокирует более поздние операции
того же подхода, поэтому stale update не отправляется и silent last-write-wins нет.
Максимум — 100 нерешённых операций; при переполнении пользователь получает ошибку,
данные не отбрасываются.

## Хранение и API

Room обновлён с версии 1 до 2 безопасной миграцией, добавляющей `workoutName` с
пустым значением по умолчанию для существующего кэша. Credentials по-прежнему не
хранятся в Room. Новых production-зависимостей и серверных/EF-миграций нет.

Клиент использует подготовленные на Этапе 13 endpoint-ы:

- `POST /api/watch/sets/{setId}/complete`;
- `PUT /api/watch/sets/{setId}`;
- `POST /api/watch/sets/{setId}/undo`.

Каждая запись несёт GUID `operationId`, `clientVersion` и диагностический UTC
timestamp. `UpdateWeight` и `UpdateReps` локально различимы, но отправляются через
единый `UpdateSet` contract с полным текущим значением подхода.

## Проверки

JVM-тесты покрывают ViewModel, сохранение редактирования, undo и haptic events.
Room/instrumentation-тесты покрывают coalescing, cancel complete+undo, удаление
подтверждённой операции, offline persistence и каскад конфликта на следующие
операции подхода. Screenshot UI-тесты проверяют current set, overview, editor и sync
status на круглом и квадратном Wear OS API 36 профилях.

API endpoint-ы и серверная optimistic concurrency были проверены integration-тестами
Этапа 13. Физические Wear OS-часы в текущем окружении отсутствуют; подключённый
Redmi Note 8 является телефоном и не использовался как подмена целевого устройства.

## Стоп-условие

Этап 14 ограничен расширенными set-операциями, offline queue и связанным UI.
Этап 15 (finish workout) не начинался.
