# Этап 12. SignalR-синхронизация с основным UI — результат

Дата завершения: 10 сентября 2026 года.

## Результат

Подход, выполненный через Watch API, появляется на уже открытой странице
`Сегодня` без ручного refresh. Этап 13 не начинался.

## Архитектурное решение

WorkoutPlanner использует Blazor Server. Каждый интерактивный компонент уже связан
с браузером аутентифицированным Blazor circuit, а его render-diff доставляется по
встроенному SignalR-соединению. Отдельного domain Hub, JavaScript SignalR client и
второго параллельного соединения до Этапа 12 не существовало.

Для текущего server-rendered UI новый Hub не требуется. Добавлен singleton
`IWorkoutRealtimeNotifier`, который:

- принимает подписку только с доверенным `userId`, полученным компонентом из
  `CurrentUserService`;
- хранит отдельный набор callback-подписок для каждого пользователя;
- публикует минимальный `WorkoutSetUpdatedNotification`: ID активной тренировки и
  авторитетное состояние одного подхода;
- изолирует ошибку одного подписчика и удаляет подписку при dispose компонента.

`WatchWorkoutService` сначала сохраняет подход и idempotency operation, затем
фиксирует транзакцию и только после commit публикует событие. Уведомление не является
путём persistence и не может изменить данные. Idempotent replay возвращает
сохранённый результат без повторной публикации, поэтому echo/duplicate loop не
возникает.

`Today.razor` применяет событие только если:

- оно пришло в подписку текущего пользователя;
- подход уже присутствует на открытой странице;
- версия события новее отображаемой версии.

Обновляется только соответствующий подход и вычисляемый прогресс, без полной
перезагрузки страницы или тренировки. Для screen reader формируется одно контекстное
`role=status` сообщение без перемещения фокуса.

## Reconnect

Кратковременный reconnect обслуживается стандартным Blazor Server circuit и
существующим `ReconnectModal`: серверное состояние компонента сохраняется и после
восстановления соединения браузер получает актуальный render state. Если circuit
утрачен и создаётся заново, `OnInitializedAsync` перечитывает авторитетное состояние
из базы. Дополнительный клиентский reconnect-loop не добавлялся.

## Безопасность

- пользовательский ID отсутствует в notification payload и не поступает от watch;
- publisher получает пользователя из аутентифицированной watch identity;
- подписка страницы получает пользователя из server-side identity;
- lookup подписчиков выполняется строго по server-side `userId`;
- integration test подтверждает, что событие получает владелец, а подписчик другого
  пользователя не вызывается;
- токены и pairing code в события и логи не попадают.

## Проверенный end-to-end сценарий

1. В браузере открыта страница `Сегодня` с тренировкой `Realtime Stage 12`.
2. До операции отображалось `Выполнено 0 из 1`, checkbox подхода был снят.
3. Синтетическое Wear OS-устройство подключено через реальные pairing endpoints.
4. `POST /api/watch/sets/{setId}/complete` сохранил подход и вернул version `1`.
5. Без reload открытая страница показала `Выполнено 1 из 1`, отмеченный checkbox и
   завершённое состояние карточки.
6. Accessibility tree содержал контекстное сообщение: подход упражнения обновлён с
   часов.

## Валидация

- Web/Test build с изолированным output: успешно, 0 ошибок; одно существующее
  предупреждение Firebase об устаревшем `Message.Token`.
- Watch-фильтр integration tests: 10/10 успешно.
- Realtime integration assertion подтверждает одну owner-targeted публикацию после
  commit, отсутствие события у другого пользователя и отсутствие второй публикации
  при idempotent replay.
- Полный server suite: 70/72 успешно при параллельном запуске. Два несвязанных
  Telegram/admin теста столкнулись с существующей process-global гонкой
  `FirebaseApp already exists`; каждый из них затем отдельно прошёл 1/1.
- EF Core `has-pending-model-changes`: изменений модели относительно последней
  миграции нет.
- Интерактивный браузерный end-to-end сценарий выполнен на отдельной временной
  SQLite-базе и описан выше.

## Границы

- новые NuGet/npm зависимости, Hub, JavaScript interop и миграции не добавлялись;
- события `WorkoutFinished`, `WatchDeviceConnected` и `WatchDeviceRevoked` не
  публикуются: они не нужны критерию Этапа 12, а завершение тренировки с часов
  относится к более позднему этапу;
- Wear OS-клиент на этом этапе не изменялся;
- реальная физическая проверка часов не требуется для механизма server-to-Blazor
  propagation; Watch API вызван настоящими watch credentials в локальном окружении.

## Стоп-условие

Критерий Этапа 12 выполнен. Расширенный Watch API Этапа 13 не начинался.
