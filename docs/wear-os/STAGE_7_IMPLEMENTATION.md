# Этап 7. Minimal Wear OS UI на mock data — результат

Дата проверки: 7 сентября 2026 года.

## Реализованный сценарий

Wear OS-клиент получил законченный UI-контур Minimal MVP на mock data:

```text
Pairing → No active workout → Refresh → Current set
        → Complete → Rest timer → Next set / Next exercise
```

- `PairingScreen` принимает шестизначный код, показывает подключение, ошибку и
  повторную попытку. Валидный demo-код — `123456`.
- `NoActiveWorkoutScreen` показывает отсутствие активной тренировки, время
  последней проверки и состояние обновления.
- `CurrentSetScreen` показывает название упражнения, номер подхода,
  индивидуальные вес и повторы только для чтения, минимальный mock sync-status и
  одно крупное действие выполнения.
- `RestTimerScreen` показывает остаток отдыха, следующий подход и явное действие
  пропуска. Пауза не добавлена: на данном этапе для неё нет продуктового
  требования.
- После последнего подхода упражнения автоматически выбирается первый
  невыполненный подход следующего упражнения.

Mock-тренировка содержит два упражнения по два подхода. Вес хранится отдельно для
каждого подхода (`80`, `82,5`, `100`, `105` кг), поэтому UI не возвращает модель
общего рабочего веса.

## Управление состоянием и таймером

Экран определяется единым `StateFlow`, которым владеет
`MinimalMvpViewModel`. Это исключает гонку между навигацией и переключением
текущего подхода: после окончания или пропуска отдыха новое состояние сразу
содержит следующий актуальный подход.

Таймер не основан на простом уменьшении счётчика. При старте сохраняется deadline
в монотонном времени (`System.nanoTime`), а отображаемый остаток каждый раз
вычисляется относительно этого deadline. Поэтому возврат из background и
перекомпозиция не растягивают отдых.

Локальное mock-выполнение применяется до перехода на таймер. Повторное нажатие
защищено проверкой текущего состояния. Реальная durable offline queue и
идемпотентная отправка на backend относятся к следующим этапам.

## Haptic feedback и фоновое срабатывание

В foreground после выполнения подхода и окончания таймера вызывается системный
`View.performHapticFeedback(HapticFeedbackConstants.CONFIRM)`. Такой способ
учитывает пользовательские настройки haptic feedback и не требует прямого
управления вибратором.

Фоновое срабатывание намеренно не реализовано на Этапе 7. Для будущей реализации
зафиксирован конкретный механизм: exact elapsed-realtime alarm через
`AlarmManager.setExactAndAllowWhileIdle(ELAPSED_REALTIME_WAKEUP)` с receiver,
который подаёт haptic только для актуального rest deadline. Перед внедрением
необходимо проверить доступность special access `SCHEDULE_EXACT_ALARM`, обработать
его отсутствие без поломки таймера и подтвердить соответствие ограничениям
энергопотребления Этапа 16. Ongoing Activity может позже дополнять индикацию, но не
является выбранным механизмом точного срабатывания; foreground service для
короткого отдыха не выбран.

## UX-решения

- Главное действие выполняется одним касанием и имеет touch target не менее
  `48 dp`.
- Критические элементы получили увеличенные внутренние отступы на круглом
  экране; общий контейнер адаптирует горизонтальные поля для круглой и квадратной
  формы.
- На текущем подходе нет промежуточного списка упражнений и нет редактирования
  веса или повторов.
- Тексты и метрики сокращены так, чтобы основной маршрут полностью помещался на
  экранах 384 × 384 и 360 × 360 без обрезания управляющих элементов.
- Для поля pairing и метрик подхода заданы осмысленные accessibility descriptions.

Стек-специфичный поиск в локальной базе `ui-ux-pro-max` не дал подтверждённых
совпадений для Jetpack Compose for Wear OS, поэтому использованы общие нативные
правила Android из skill: безопасные края, минимальный touch target `48 dp`,
короткие подписи и один доминирующий action.

## Проверка

В каталоге `WorkoutPlanner.WearOS` выполнено:

```powershell
.\gradlew.bat testDebugUnitTest lintDebug assembleDebug
```

Результат: `BUILD SUCCESSFUL`, 57 задач. Выполнено 5 unit-тестов, failures/errors
нет. Тестами покрыты ошибка и retry pairing, успешный pairing и refresh,
переходы к следующему подходу и упражнению, монотонный deadline и округление
остатка таймера.

Debug APK установлен и проверен реальными ADB-касаниями:

- круглый Wear OS 6 / API 36 emulator, 384 × 384;
- квадратный Wear OS 6 / API 36 emulator, 360 × 360.

На обоих профилях проверены pairing, отсутствие тренировки, refresh, текущий
подход и экран отдыха. На круглом профиле подтверждён автоматический переход после
таймера и корректный пересчёт deadline после ухода на watch face и возврата в
приложение. На квадратном профиле подтверждён ручной путь
`Выполнить → Пропустить → подход 2`, включая смену индивидуального веса с `80` на
`82,5` кг. Физическую силу вибрации эмулятор подтвердить не может; проверен вызов
foreground haptic-кода, но не аппаратный отклик часов.

## Границы этапа

Production API, настоящее pairing, Room, WorkManager sync, offline queue,
редактирование веса/повторов, undo, finish workout, workout overview и расширенная
обработка конфликтов не реализованы. Миграции и серверный код на Этапе 7 не
изменялись.

## Стоп-условие

Критерий Этапа 7 выполнен: mock-цикл
`CurrentSet → Complete → RestTimer → NextSet / NextExercise` работает. Работа
остановлена до начала Этапа 8.
