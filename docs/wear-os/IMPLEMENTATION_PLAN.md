# Wear OS Integration — Implementation Plan

## 1. Назначение документа

Этот документ описывает поэтапную реализацию поддержки часов на Wear OS для проекта `WorkoutPlanner`.

Основная цель функции: пользователь должен иметь возможность открыть активную тренировку на часах, просматривать упражнения и подходы, отмечать выполнение подходов, изменять фактический вес и количество повторений, запускать таймер отдыха и синхронизировать изменения с основным приложением.

Документ предназначен для пошаговой работы агента Codex.

---

## 2. Общие правила выполнения

1. Выполнять только тот этап, который явно указан пользователем.
2. Не переходить к следующему этапу автоматически.
3. Перед изменением кода изучить существующую реализацию.
4. Не придумывать новые сущности, если в проекте уже есть подходящие модели или сервисы.
5. Не дублировать существующую бизнес-логику.
6. Не переносить бизнес-логику тренировок в Wear OS-клиент.
7. После каждого этапа:
   - запустить сборку;
   - запустить доступные тесты;
   - перечислить изменённые файлы;
   - описать принятые решения;
   - сообщить о нерешённых проблемах;
   - предложить название Git-коммита.
8. Не выполнять автоматический Git commit или push, если пользователь явно этого не попросил.
9. Не удалять существующий функционал приложения ради упрощения интеграции.
10. Не выполнять массовый рефакторинг, не связанный с текущим этапом.

## 3. Целевая архитектура

```text
WorkoutPlanner.Web / мобильный клиент
                │
                │ HTTPS API
                ▼
WorkoutPlanner Backend
                │
                │ База данных
                ▼
      Активные тренировки
                ▲
                │ HTTPS API
                │
       Wear OS приложение
```

Дополнительно основной Blazor-интерфейс может получать изменения в реальном времени через SignalR:

```text
Wear OS
   │
   ▼
REST API
   │
   ├── Сохранение в базе
   │
   └── SignalR-событие
              │
              ▼
     Открытая Blazor-страница
```

Wear OS-приложение должно быть отдельным клиентом системы. Оно не должно напрямую обращаться к базе данных и не должно зависеть от внутренних классов Entity Framework.

## 4. Уровни функционального объёма

Интеграция реализуется в два уровня. Это обязательное правило порядка разработки.

### 4.1 Minimal MVP — первая реально рабочая версия

Minimal MVP должен доказать основной сценарий использования часов во время тренировки:

```text
Подключить часы
        ↓
Получить активную тренировку
        ↓
Показать текущее упражнение
        ↓
Показать текущий подход
        ↓
Нажать один крупный чекбокс выполнения
        ↓
Сохранить действие локально
        ↓
Запустить таймер отдыха
        ↓
Синхронизировать выполнение с сервером
        ↓
Показать следующий подход / следующее упражнение
```

В Minimal MVP входят:

- безопасное подключение часов к аккаунту;
- отдельная аутентификация watch device;
- получение активной тренировки;
- определение текущего упражнения и текущего невыполненного подхода;
- отображение названия упражнения;
- отображение номера текущего подхода;
- отображение веса и повторений только для чтения, если эти данные уже есть в модели;
- один крупный элемент выполнения текущего подхода;
- локальное сохранение действия до сетевого ответа;
- автоматический запуск таймера отдыха после локального выполнения подхода;
- корректная работа таймера после навигации, background и повторного открытия приложения;
- переход к следующему невыполненному подходу;
- переход к следующему упражнению после последнего подхода текущего упражнения;
- минимальный статус синхронизации;
- повторная отправка после временной потери сети;
- идемпотентность операции выполнения;
- end-to-end проверка с реальным backend.

Minimal MVP **не должен блокироваться** следующими функциями:

- редактирование веса на часах;
- редактирование повторений на часах;
- полноценный обзор всей тренировки;
- завершение тренировки с часов;
- сложный экран конфликтов;
- полноценное управление всеми подключёнными устройствами;
- SignalR-обновление открытого Blazor UI;
- Health Connect;
- датчики пульса и калорий;
- голосовое управление;
- Apple Watch.

### 4.2 Extended Wear OS — расширение после Minimal MVP

Только после успешной проверки Minimal MVP добавляются:

- отмена выполнения подхода;
- изменение фактического веса;
- изменение фактических повторений;
- полноценный список упражнений и прогресс по тренировке;
- завершение тренировки с часов;
- полный UI состояния синхронизации;
- расширенная обработка конфликтов версий;
- полноценная страница подключённых устройств;
- SignalR-синхронизация с открытым основным интерфейсом;
- дополнительные сценарии отказоустойчивости и release-hardening.

### 4.3 Общие ограничения MVP

На обоих уровнях не входят без отдельного запроса:

- измерение пульса;
- подсчёт калорий;
- Health Connect;
- автоматическое распознавание упражнений;
- управление тренировкой голосом;
- NFC;
- поддержка Apple Watch;
- сложная аналитика на часах;
- Bluetooth Data Layer как обязательный основной канал;
- автоматический выбор веса или автоматическая прогрессия нагрузки.

Архитектурные требования безопасности, server-as-source-of-truth, offline-first и идемпотентность не считаются «расширенными фичами» и должны закладываться с Minimal MVP.

# Этап 1. Выделение прикладных операций тренировки

## Цель

Подготовить серверную бизнес-логику так, чтобы одни и те же операции могли безопасно использовать Blazor-интерфейс и Wear OS API.

## Задачи

1. Найти текущую логику:
   - выполнения подхода;
   - отмены выполнения;
   - изменения веса;
   - изменения повторений;
   - завершения тренировки.
2. При необходимости выделить интерфейс прикладного сервиса, например:

```csharp
public interface IActiveWorkoutService
{
    Task<ActiveWorkoutDto?> GetActiveWorkoutAsync(
        string userId,
        CancellationToken cancellationToken);

    Task<WorkoutSetDto> UpdateSetAsync(
        string userId,
        long setId,
        UpdateWorkoutSetCommand command,
        CancellationToken cancellationToken);

    Task FinishWorkoutAsync(
        string userId,
        long workoutId,
        CancellationToken cancellationToken);
}
```

3. Названия и типы должны соответствовать фактической структуре проекта.
4. Существующий Blazor UI по возможности должен использовать этот же сервис.
5. Проверка владельца тренировки должна находиться на сервере.
6. Не доверять `UserId`, переданному клиентом.
7. Все запросы должны поддерживать `CancellationToken`.
8. Изменения должны сохраняться атомарно.
9. Не изменять значения подходов других пользователей.
10. Добавить тесты прикладной логики.

## Критерий готовности

Сервер имеет переиспользуемые операции активной тренировки без привязки к конкретной Blazor-странице.

# Этап 2. Модель подключения часов

## Цель

Добавить серверные сущности, необходимые для безопасного подключения Wear OS-устройства.

## Предлагаемые сущности

Имена разрешается адаптировать к стилю проекта.

### WatchDevice

Возможные поля:

```text
Id
UserId
DeviceId
DisplayName
Platform
CreatedAtUtc
LastSeenAtUtc
RevokedAtUtc
RefreshTokenHash
RefreshTokenExpiresAtUtc
AppVersion
DeviceModel
```

Требования:

- один пользователь может иметь несколько устройств;
- отключённое устройство не должно получать доступ к API;
- refresh token не хранить в открытом виде;
- уникальность `DeviceId` должна быть продумана;
- удаление пользователя должно корректно обрабатывать связанные устройства.

### WatchPairingCode

Возможные поля:

```text
Id
UserId
CodeHash
CreatedAtUtc
ExpiresAtUtc
UsedAtUtc
AttemptCount
```

Требования:

- код одноразовый;
- код имеет ограниченный срок действия;
- код хранится в виде хеша;
- должна быть защита от перебора;
- использованный код нельзя применить повторно.

### WatchSyncOperation

Создавать отдельную серверную таблицу только в том случае, если она действительно нужна для идемпотентности.

Возможные поля:

```text
OperationId
WatchDeviceId
OperationType
EntityId
ReceivedAtUtc
Result
```

Альтернатива: хранить обработанные operation ID в существующей инфраструктуре или отдельном idempotency store.

## Задачи

1. Добавить сущности.
2. Добавить конфигурации EF Core.
3. Добавить индексы и ограничения.
4. Добавить навигационные свойства только при необходимости.
5. Создать миграцию.
6. Проверить SQLite-совместимость, если проект использует SQLite.
7. Добавить тесты ограничений модели.

## Критерий готовности

База данных поддерживает подключение, отзыв и идентификацию часов.

# Этап 3. API подключения устройства

## Цель

Реализовать безопасное подключение часов к аккаунту.

## Предлагаемый сценарий

1. Авторизованный пользователь в основном приложении создаёт одноразовый код.
2. Пользователь вводит код на часах.
3. Часы отправляют код и сведения об устройстве.
4. Сервер проверяет код.
5. Сервер создаёт `WatchDevice`.
6. Сервер возвращает пару access/refresh token либо другой принятый в проекте механизм.
7. Код помечается использованным.

## Предлагаемые endpoints

### Создание кода

```http
POST /api/watch/pairing-codes
```

Требования:

- доступен только авторизованному пользователю;
- старые активные коды пользователя могут инвалидироваться;
- ответ не должен содержать секреты, кроме самого одноразового кода;
- срок действия должен возвращаться явно.

### Подключение часов

```http
POST /api/watch/pair
```

Пример запроса:

```json
{
  "code": "482913",
  "deviceId": "device-generated-stable-id",
  "displayName": "Galaxy Watch",
  "deviceModel": "SM-R960",
  "appVersion": "1.0.0"
}
```

### Обновление токена

```http
POST /api/watch/token/refresh
```

### Отключение часов

```http
DELETE /api/watch/devices/{deviceId}
```

### Список устройств

```http
GET /api/watch/devices
```

## Безопасность

- добавить rate limiting;
- логировать подозрительные попытки без сохранения полного кода;
- access token должен быть короткоживущим;
- refresh token должен отзываться;
- устройство должно иметь отдельную identity/claim;
- API должно отличать обычного пользователя от watch device;
- не использовать пароль пользователя на часах;
- не возвращать лишние персональные данные;
- не принимать `UserId` из тела запроса как источник истины.

## Критерий готовности

Часы можно безопасно подключить, обновить токен и отключить.

# Этап 4. Minimal Watch API активной тренировки

## Цель

Предоставить часам только тот серверный API, который необходим для первого рабочего цикла «текущий подход → выполнить → следующий подход».

На этом этапе не создавать универсальный API редактирования веса/повторов и не реализовывать завершение тренировки.

## Предлагаемые endpoints

### Получение активной тренировки

```http
GET /api/watch/workouts/active
```

Минимальный DTO должен содержать только данные, нужные Minimal MVP:

```text
WorkoutId
WorkoutName
StartedAtUtc
Version
Exercises[]
```

Упражнение:

```text
ExerciseId
Name
Order
Sets[]
```

Подход:

```text
SetId
SetNumber
PlannedWeight
PlannedReps
ActualWeight
ActualReps
IsCompleted
CompletedAtUtc
Version
```

Если существующая модель позволяет безопасно определить это на сервере, дополнительно полезно вернуть:

```text
CurrentExerciseId
CurrentSetId
```

Если таких понятий в текущей архитектуре нет, не вводить их искусственно до анализа. Допускается детерминированно выбирать первый невыполненный подход по существующему порядку упражнений и подходов.

### Выполнение текущего подхода

Предпочтительная узкая операция:

```http
POST /api/watch/sets/{setId}/complete
```

Пример запроса:

```json
{
  "operationId": "b92f4a4f-a588-4a7b-bf68-c19884f9ab44",
  "changedAtUtc": "2026-08-05T17:20:00Z",
  "clientVersion": 3
}
```

Названия полей и route адаптировать к фактической архитектуре проекта.

## Требования

- не возвращать EF Entity напрямую;
- пользователь определяется по аутентифицированному watch device;
- не принимать `UserId` из JSON как источник истины;
- проверить, что устройство активно;
- проверить, что тренировка принадлежит пользователю;
- проверить, что подход принадлежит активной тренировке;
- повторный `operationId` не должен повторно применять действие;
- после выполнения сервер возвращает авторитетное актуальное состояние подхода и достаточно данных для определения следующего шага;
- корректно обрабатывать отсутствие активной тренировки;
- корректно обрабатывать уже завершённую тренировку;
- сохранять серверные timestamps в UTC;
- не добавлять редактирование веса, повторений или finish endpoint на этом этапе.

## Минимальная стратегия конфликта

Minimal MVP не должен строить сложный conflict UI, но сервер обязан обнаруживать явную потерю актуальности.

Если операция не может быть безопасно применена из-за изменившегося состояния:

```http
409 Conflict
```

Ответ должен содержать текущее серверное состояние подхода или активной тренировки, достаточное для refresh.

## Тесты

Добавить как минимум:

- получение своей активной тренировки;
- запрет доступа к чужой тренировке;
- выполнение своего подхода;
- запрет выполнения чужого подхода;
- повторный `operationId`;
- revoked device;
- отсутствие активной тренировки;
- конфликт устаревшего состояния, если версия используется моделью.

## Критерий готовности

Через Swagger/API-тесты можно:

1. аутентифицировать watch device;
2. получить активную тренировку;
3. выполнить конкретный подход;
4. повторно отправить ту же операцию без двойного применения;
5. получить актуальное серверное состояние.

# Этап 5. Минимальный UI подключения часов в основном приложении

## Цель

Дать пользователю минимальный пользовательский путь для подключения часов, не создавая пока полноценную страницу управления устройствами.

## Функции

- действие «Подключить часы»;
- создание одноразового pairing code;
- отображение кода;
- отображение времени его действия;
- короткая инструкция «введите этот код на часах»;
- loading/error/success состояния.

## Не входит на этом этапе

- переименование устройств;
- подробный список устройств;
- last seen;
- отзыв всех часов;
- расширенный device-management UI.

Эти функции будут добавлены после Minimal MVP.

## Критерий готовности

Пользователь может получить pairing code из основного приложения без Swagger и использовать его для подключения часов.

# Этап 8. Минимальная локальная база и offline-first

## Цель

Сделать основное действие Minimal MVP безопасным при нестабильной сети.

## Локальные сущности

Минимально допустимы:

```text
LocalWorkout
LocalExercise
LocalWorkoutSet
PendingSyncOperation
DeviceSessionMetadata
```

Не смешивать Room entities с network DTO без необходимости.

## PendingSyncOperation

Минимальные поля:

```text
OperationId
OperationType
EntityId
PayloadJson
CreatedAtUtc
AttemptCount
LastAttemptAtUtc
LastError
Status
```

Статусы:

```text
Pending
Syncing
Synced
Failed
Conflict
```

## Алгоритм выполнения подхода

1. Пользователь нажимает completion control.
2. Локальный `LocalWorkoutSet` обновляется сразу.
3. Генерируется уникальный `operationId`.
4. Операция атомарно сохраняется в Room вместе с локальным изменением.
5. UI сразу запускает таймер отдыха.
6. WorkManager планирует синхронизацию.
7. При успехе локальный подход заменяется/подтверждается авторитетным серверным состоянием.
8. Операция помечается `Synced`.
9. При временной ошибке применяется retry с backoff.
10. При `401` допускается один нормальный refresh-token flow.
11. При `409` операция переводится в `Conflict`, данные обновляются с сервера, UI не делает тихий overwrite.

## Требования

- pending operation переживает process death;
- переживает перезапуск часов;
- UI не ждёт сеть для отметки подхода;
- не создавать отдельный WorkManager job на каждый tap, если очередь можно обработать безопасно;
- токены не хранить обычным текстом в Room;
- использовать Android Keystore-backed storage;
- не логировать токены;
- порядок операций одной сущности должен сохраняться;
- для Minimal MVP достаточно одного типа mutation: `CompleteSet`.

## Критерий готовности

На mock/fake network можно:

1. отключить сеть;
2. выполнить подход;
3. увидеть локально завершённый подход и таймер;
4. перезапустить приложение;
5. восстановить сеть;
6. отправить pending operation без потери и дубля.

# 5. Definition of Done

## 5.1 Definition of Done Minimal MVP

Minimal MVP завершён, когда:

1. Пользователь создаёт pairing code в основном приложении.
2. Часы безопасно подключаются к аккаунту.
3. Watch credentials можно обновлять и отзывать.
4. Часы получают реальную активную тренировку.
5. На часах отображается текущее упражнение.
6. Отображается текущий подход.
7. Выполнение подхода доступно одним крупным действием.
8. Изменение сначала надёжно сохраняется локально.
9. Таймер отдыха стартует немедленно после локального выполнения.
10. Таймер переживает обычную навигацию/background.
11. После отдыха выбирается следующий невыполненный подход.
12. После последнего подхода упражнения выбирается следующее упражнение.
13. Offline completion не теряется.
14. После возвращения сети pending operation отправляется на сервер.
15. Повторная отправка одного operation ID не создаёт дубль.
16. Revoked device теряет доступ.
17. Server остаётся source of truth.
18. Основной end-to-end сценарий проверен на Wear OS Emulator, а при доступности — на физических часах.

Только после выполнения этого списка начинать Extended Wear OS.

## 5.2 Definition of Done всей функции

Полная интеграция завершена, когда дополнительно:

1. Пользователь управляет списком подключённых часов.
2. Подходы можно при необходимости отменять и редактировать с часов.
3. Изменение веса/повторов не нарушает серверную бизнес-логику.
4. Конфликты обнаруживаются и не приводят к silent overwrite.
5. SignalR корректно обновляет открытый основной UI, если он используется.
6. Тренировку можно безопасно завершить с часов.
7. История тренировки остаётся корректной.
8. Security/offline/concurrency сценарии покрыты тестами.
9. Release configuration валидирована.
10. Документация актуальна.
