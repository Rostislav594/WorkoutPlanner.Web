# Contextual Help System

## Цель
Поддерживать простую и масштабируемую систему помощи GymPlanner.

Основная модель: `Страница → ? → руководство текущего раздела`.

Не возвращаться к сложному пошаговому onboarding без отдельного запроса пользователя.

## Перед началом
1. Прочитать применимые `AGENTS.md`.
2. Изучить существующую Help System.
3. Найти legacy onboarding.
4. Изучить layout, страницы и shared UI.
5. Найти CSS/design tokens.
6. Найти механизм пользовательских настроек.
7. Найти каталог иллюстраций и персонажей.
8. Не создавать дубли существующих компонентов.

## Основное правило
Help System — контекстная справка, а не интерактивный тур.

Без отдельного запроса не создавать:
- длинные onboarding-последовательности;
- автоматическую навигацию;
- spotlight для каждого элемента;
- `Назад / Далее`;
- обязательное обучение;
- сложные графы шагов.

Дополнительное обязательное правило по персонажу Contextual Help System:

Для Contextual Help System использовать персонажа ТОЛЬКО из предоставленного пользователем изображения/референса по пути, указанному во вложении или в проекте.

Это изображение является единственным утверждённым источником внешнего вида персонажа.

Codex НЕ должен:
- перерисовывать персонажа;
- генерировать новые версии;
- менять лицо;
- менять телосложение;
- менять причёску;
- менять одежду;
- менять цвета;
- менять логотип GP;
- менять стиль рисовки;
- дорисовывать новые эмоции или позы;
- создавать альтернативную интерпретацию персонажа.

Разрешается выполнять только техническую обработку существующего изображения, если это необходимо для корректного использования в Contextual Help System.

Разрешается:
- вырезать нужного персонажа из общего изображения;
- кадрировать изображение;
- удалять лишнее пространство;
- удалять фон;
- делать фон прозрачным;
- уменьшать изображение;
- увеличивать изображение без заметной потери качества;
- улучшать техническое качество изображения при масштабировании;
- оптимизировать размер файла;
- конвертировать формат изображения;
- подготавливать отдельные PNG/WebP-ассеты;
- адаптировать размеры под Desktop и Mobile;
- располагать персонажа в разных местах Help Dialog/Help Sheet.

При любой обработке необходимо сохранять оригинальную структуру персонажа и его визуальную идентичность.

Если изображение содержит несколько уже существующих вариантов персонажа с разными эмоциями или позами, Codex должен:
1. использовать только эти существующие варианты;
2. при необходимости вырезать их в отдельные ассеты;
3. давать им понятные имена файлов;
4. выбирать подходящий вариант интуитивно по контексту конкретного Help Section.

Пример структуры ассетов:

assets/help/characters/
    character-friendly.png
    character-thinking.png
    character-pointing.png
    character-surprised.png
    character-positive.png

Названия должны соответствовать фактическим существующим позам/эмоциям на исходном изображении.

Если для конкретного контекста нет идеально подходящей позы или эмоции, использовать наиболее близкий существующий вариант.

НЕ создавать новый вариант персонажа самостоятельно.

Если увеличение приводит к заметной пикселизации, размытиям или артефактам, выбрать максимально допустимый размер без визуальной деградации.

Запрещается непропорциональное растягивание изображения.

После подготовки ассетов Codex должен использовать только полученные из исходного референса изображения персонажа во всей Contextual Help System.

## Help Button
Использовать общий переиспользуемый компонент `?`.

Он должен:
- находиться в предсказуемом месте;
- не конкурировать с основным CTA;
- соответствовать GymPlanner;
- иметь accessible label;
- работать на Desktop и Mobile.

## First Help Hint
Один раз объяснить новому пользователю назначение `?`:
1. страница рендерится;
2. интерфейс затемняется;
3. `?` выделяется;
4. показывается короткое сообщение;
5. пользователь закрывает его;
6. сохраняется `HasSeenHelpIntroduction`;
7. подсказка больше автоматически не появляется.

## Help Dialog / Help Sheet
Desktop: крупный dialog/modal.

Mobile: full-screen или near-full-screen sheet/page.

Окно должно поддерживать длинное структурированное руководство.

## Контент
Каждый Help Topic относится к конкретному разделу и состоит из тематических Sections.

Предпочтительная структура:
`заголовок → иллюстрация → короткое объяснение`

Для сложных действий иллюстрации обязательны.

## Иллюстрации
Предпочитать:
1. актуальные фрагменты реального UI;
2. annotated screenshots;
3. схемы;
4. персонажа как вспомогательный элемент.

При изменении UI проверять связанные изображения.

## Персонаж
Использовать только существующие изображения.

Запрещено:
- генерировать нового персонажа;
- менять лицо, тело, одежду, стиль и цвета;
- дорисовывать новые эмоции.

Разрешено:
- crop;
- удаление пустого пространства;
- прозрачный фон;
- resize;
- увеличение без заметной деградации;
- уменьшение.

Не деформировать пропорции.

Эмоцию/позу выбирать интуитивно по смыслу текущего раздела.

## Архитектура
Разделять:
- UI кнопки;
- UI руководства;
- данные;
- иллюстрации;
- пользовательское состояние.

Не копировать полноценную реализацию Help Dialog на каждую страницу.

## Legacy onboarding
При замене старого onboarding:
1. найти зависимости;
2. проверить компоненты;
3. проверить сервисы;
4. проверить CSS;
5. проверить JS Interop;
6. проверить persistence;
7. удалить только неиспользуемые части;
8. собрать проект;
9. проверить runtime.

Не оставлять мёртвый onboarding-код без причины.

## Содержание
Не выдумывать функциональность.

Перед написанием инструкции:
1. изучить страницу;
2. изучить код;
3. при возможности запустить приложение;
4. определить реальный user flow;
5. только затем писать руководство.

## Проверка
Для каждого Help Topic проверить:
- правильную страницу;
- заголовок;
- актуальность текста;
- актуальность изображений;
- открытие/закрытие;
- scroll;
- Desktop;
- Mobile;
- overflow;
- keyboard;
- focus;
- accessibility.

## Синхронизация
Если изменяется функция, для которой существует Help Section, обязательно проверить необходимость обновления руководства.

Устаревшую справку не оставлять.

## Итоговый отчёт
Указать:
- изменённые Help Topics;
- страницы с `?`;
- используемые изображения;
- удалённые legacy onboarding-компоненты;
- место хранения `HasSeenHelpIntroduction`;
- проверки Desktop/Mobile;
- инструкции, требующие будущего обновления.

## Главный принцип
**доступная → контекстная → визуальная → необязательная → повторно открываемая → простая в сопровождении**
